# Signal analysis — what information the methods use, and whether it is shared

_Follow-up to `REVIEW.md` / `report.md`. Explores the question: what information
do the methods actually use to predict, and are they finding the **same**
informative signal or **different / unique** sources? Analysis run against the
real TrialBench data locally, using the repo's own leakage-safe loader +
featurizer._
_Date: 2026-07-24_

---

## 1. Question and scope

Two linked questions:

1. **What information drives the predictions?** Which features does each method
   rely on?
2. **Same or unique signal?** Do different methods key on the same informative
   features / rank the same trials, or do they exploit different sources?

Scope of this first cut: two representative **binary** cells — `outcome/Phase1`
(trial approval) and `mortality_rate_yn/Phase1` — single seed (42), across the
12 Tier A methods plus `tfidf_logreg`. Deep methods (`ft_transformer`, `tabnet`,
`clinical_embeddings`) are **not** covered here — see §5.

---

## 2. The central gap: the saved results cannot answer this

Every record in `results/runs/*.json` is **metrics-only** — AUROC, PR-AUC, F1,
timings, and the bootstrap. There are **no coefficients, no feature importances,
no saved models, and no stored predictions**. So nothing about *what the models
use* was ever persisted, and this question cannot be answered from the current
results at all.

Everything below was therefore **regenerated by refitting** from the raw data
(present locally under `data/`) through the repo's own `load_task_phase` +
`TabularFeaturizer` — the identical, leakage-safe path used in production. The
analysis touches nothing in `results/`.

**Implication for the harness:** to make this answerable going forward, the
runner should persist per-method attributions (or at least the test-set
predictions), so signal analysis doesn't require a full refit each time.

---

## 3. Method

- **Feature attribution — permutation importance on the test set**, scored by
  PR-AUC (the benchmark's headline metric): shuffle one feature column, measure
  the drop in PR-AUC. This is model-agnostic and comparable across model types,
  and every tabular method sees the identical feature space, so importances are
  directly comparable. Native importances (`|coef|` for linear,
  `feature_importances_` for trees/GBMs) were extracted as a cross-check.
- **Prediction-level agreement** — Spearman correlation of each method's
  predicted `P(y=1)` on the test set (do methods rank the same trials high?),
  plus top-decile overlap (Jaccard of the trials each method scores highest).
- **Tabular + text fusion** — blend a tabular consensus score (rank-mean of the
  tabular methods) with the `tfidf_logreg` score; the blend weight is tuned on
  the **validation** split and reported on **test**. If the blend beats the best
  single source, text carries information the tabular view does not.
- `tfidf_logreg` lives in a **different feature space** (≈50k TF-IDF tokens over
  free text), disjoint from the ≈38–43 engineered tabular columns, so it is
  characterised separately by its top tokens and treated as its own "source" in
  the agreement/fusion analysis.

Scripts (in the session outputs): `feature_signal_probe.py`,
`prediction_agreement.py`.

---

## 4. Findings

### 4.1 What information drives the predictions — and it is task-appropriate

The tabular methods converge on a small shared core of features that shifts
sensibly with the task. "Consensus" below = how many of the 10 tabular methods
place the feature in their own top-12 by permutation importance.

**Trial approval (`outcome/Phase1`, 38 features, test positive rate 0.431):**

| Feature | Consensus |
|---|---|
| `study_design_info/primary_purpose` (target-enc.) | 10 / 10 |
| `enrollment` (trial size) | 9 / 10 |
| `location/facility/address/city` (target-enc.) | 9 / 10 |
| `study_design_info/intervention_model` (target-enc.) | 9 / 10 |
| `sponsors/lead_sponsor/agency_class` (industry vs academic) | 8 / 10 |
| `number_of_arms`, arm/intervention counts | 6–7 / 10 |

**Mortality (`mortality_rate_yn/Phase1`, 43 features, test positive rate 0.270):**

| Feature | Consensus |
|---|---|
| `eligibility/maximum_age` (target-enc.) | 10 / 10 |
| `location/facility/address/city` (target-enc.) | 9 / 10 |
| `eligibility/healthy_volunteers` | 7 / 10 |
| `study_design_info/primary_purpose` | 7 / 10 |
| `enrollment`, intervention counts, `is_fda_regulated_device`, `agency_class`, `intervention_model` | 6 / 10 |

The cores are different and clinically plausible: trial approval keys on
scale / design / sponsor; mortality keys on age and healthy-volunteer status
(older / sicker populations, non-healthy-volunteer trials → higher mortality).
So the methods are keying on task-appropriate signal, not a fixed feature set.

One feature to scrutinise: the target-encoded `facility city` is highly
important in **both** tasks. For a high-cardinality target-encoded field this
smells like an encoding artifact (or leakage) rather than a real causal signal,
and deserves a dedicated check.

### 4.2 The tabular methods are largely redundant with each other

At the very top of the ranking the methods agree strongly, but the fuller
importance ranking diverges — mean pairwise Spearman of the importance vectors
is only **0.26** (approval) and **0.22** (mortality).

At the prediction level the picture is clearer: the gradient-boosted trees
(random forest, extra trees, HistGBM, XGBoost, LightGBM, CatBoost) rank the same
trials high — score correlations of **0.7–0.9** on approval. They are mostly
finding the **same** signal and are redundant with one another.

Per-cell PR-AUC (regenerated; single seed 42):

| Method | approval/P1 | mortality/P1 |
|---|---|---|
| logreg_l2 | 0.648 | 0.756 |
| logreg_l1 | 0.431 | 0.591 |
| svm_linear | 0.460 | 0.536 |
| knn | 0.595 | 0.781 |
| random_forest | 0.662 | 0.787 |
| extra_trees | 0.631 | 0.817 |
| hist_gbm | 0.595 | 0.656 |
| xgboost | 0.663 | 0.767 |
| lightgbm | 0.684 | 0.718 |
| catboost | 0.642 | 0.455 |
| **tfidf_logreg** | **0.658** | **0.856** |

**Caveat on "outliers."** Some methods correlate weakly with everything —
`logreg_l1` and `svm_linear` on approval, `catboost` on mortality. But these are
**degenerate**, not insightful: their PR-AUC collapses to roughly the base rate
(0.431 / 0.460 vs prior 0.431; 0.455 vs prior 0.270). Low correlation there
signals failure, not a unique source of signal. This is why decorrelation alone
is not sufficient evidence of "unique information" — it has to be paired with the
method actually working.

### 4.3 Text (`tfidf_logreg`) is a distinct, additive source

`tfidf_logreg` works on a feature space completely disjoint from the tabular
columns, yet it is competitive (approval, 0.658) or the single best method
(mortality, 0.856). It is meaningfully decorrelated from the tabular pack on
approval (mean tabular–tfidf score correlation **0.30** vs tabular–tabular
**0.39**), and even where the overall ranking is similar (mortality: 0.67 vs
0.67) it picks different trials in the crucial top decile (Jaccard **0.21** vs
tabular–tabular **0.30**).

The decisive test is fusion (blend weight tuned on validation, scored on test):

| Cell | Best single tabular | Text (tfidf) | Tabular + text blend | Lift over best single |
|---|---|---|---|---|
| approval/P1 | 0.706 (consensus) | 0.659 | **0.736** (0.70 tab / 0.30 text) | **+0.053** |
| mortality/P1 | 0.817 (extra_trees) | 0.856 | **0.874** (0.25 tab / 0.75 text) | **+0.018** |

Fusing beats the best single source in both cells, and the optimal mix flips by
task: on approval, structured design/scale features lead and text tops them up;
on mortality, disease-severity text dominates and structured features top *it*
up. This is direct evidence that text and tabular carry **complementary**
information, not the same signal repackaged.

### 4.4 The text signal, in words

Top TF-IDF tokens by logistic-regression coefficient:

- **Approval — positive:** vaccine, vaccination, solid, advanced, "mg m2",
  diabetes, "solid tumors", safety, immunogenicity, "advanced solid".
  **Negative:** leukemia, covid / "covid 19", biopsy, transplant, undergo.
- **Mortality — positive:** tumor, solid, therapy, advanced, tumors, metastatic,
  chemotherapy, "solid tumors", grade. **Negative:** healthy, screening,
  "single dose", placebo, kg, body, mass.

So the text model is encoding therapeutic area, disease severity, and trial
modality (advanced/metastatic oncology → high mortality; healthy-volunteer /
single-dose PK trials → low) — information the tabular view largely lacks,
because the featurizer excludes the free-text, SMILES, ICD, and MeSH columns.

## 5. `ft_transformer` — open question (could not run here)

The natural counterpart question — *what data does `ft_transformer` find, and is
it orthogonal to `tfidf`?* — could **not** be answered in this environment.
`ft_transformer` requires PyTorch, and torch will not install in this sandbox:
the CPU wheel index (`download.pytorch.org`) is blocked by the proxy (403), and
the default PyPI build is unavailable/too large to pull here. (The same
limitation is noted in `report.md` §4.1.)

What can be said structurally, without running it:

- `ft_transformer` has `feature_view = "tabular"` — it sees the **same** ≈38–43
  engineered columns as the other tabular methods, and it **cannot** see the
  free-text tokens `tfidf_logreg` uses. So it draws from the same information
  pool as the tabular pack, and any overlap with `tfidf` can only come from
  structured features that happen to correlate with the text-derived signal.
- On that basis, `ft_transformer` is very unlikely to be *orthogonal* to the
  tabular methods, and is likely **partially** overlapping with `tfidf` (to the
  same extent the tabular pack already is: ~0.30 correlation on approval, higher
  on mortality). But this is a structural expectation, **not a measurement**.
- For reference, its real-benchmark PR-AUC (from the leaderboard) on these two
  cells is 0.682 (approval/P1) and 0.809 (mortality/P1).

**How to actually answer it:** run `ft_transformer` on the EC2 box (torch is
installed there), capture its test-set predictions on `outcome/Phase1` and
`mortality_rate_yn/Phase1`, and feed those through the same
`prediction_agreement.py` analysis used above — i.e. correlate its scores with
`tfidf` and with the tabular pack, and test an `ft_transformer + tfidf` fusion
for lift. If the blend adds lift, its signal is (partly) orthogonal to text;
if not, it is largely redundant with what text already captures.

## 6. Caveats and limits

- **Two of 20 cells, single seed, Tier A + tfidf only.** Not yet the other
  phases, the other tasks (`serious_adverse`, `patient_dropout`), the multiclass
  `failure_reason` (which needs per-class attribution), or the deep/embedding
  methods.
- **Different feature spaces are not directly comparable.** Tabular (38–43
  columns), text (≈50k tokens), and clinical embeddings (768-dim) live in
  disjoint spaces; the "same vs unique" claim rests on the prediction-level
  agreement and fusion, not on lining up feature axes.
- **Permutation importance** can be distorted by correlated features; the
  target-encoded `facility city` result specifically needs a leakage check.
- **The featurizer discards modalities** (text / SMILES / ICD / MeSH) before any
  tabular model sees them — so "the information used" by the tabular methods is
  already a filtered subset, which is part of why text alone is competitive.

## 7. Recommended next steps

1. **Answer the `ft_transformer` question on EC2** (run it, capture predictions,
   run `prediction_agreement.py`), and include `clinical_embeddings` — it is
   *also* text-based, so a key sub-question is whether it finds the same signal
   as `tfidf`.
2. **Investigate the `facility city` feature** — is its importance real signal
   or a target-encoding artifact / leakage?
3. **Extend both probes across the full grid**, including `failure_reason`.
4. **Persist predictions (and ideally importances) in the harness**, so signal
   analysis is answerable from `results/` without refitting.
5. Given the consistent fusion lift, **consider an explicit tabular + text model**
   as a benchmark entry rather than treating text and tabular as separate rows.

## 8. Reproduce

```bash
# from repo root, with the Tier A stack + real data present
PYTHONPATH=. python3 feature_signal_probe.py   --task outcome           --phase Phase1
PYTHONPATH=. python3 feature_signal_probe.py   --task mortality_rate_yn --phase Phase1
PYTHONPATH=. python3 prediction_agreement.py   --task outcome           --phase Phase1
PYTHONPATH=. python3 prediction_agreement.py   --task mortality_rate_yn --phase Phase1
```

Each writes a JSON summary (feature names, importances, correlation matrix,
consensus votes, fusion result) and prints a readable report. Neither touches
`results/`.
